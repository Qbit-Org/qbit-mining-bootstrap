## Ranked findings

### 1. HIGH — the "original revision fence" test asserts a helper the runtime never calls; the runtime refusal is only `is_err()`
- support/b275_persistence_measure/mod.rs:419-444 drives `Ledger::save_job` and asserts its message "payout revision changed during job construction".
- At base, `save_job` (src/ledger/jobs.rs:28-58) has no runtime callers; the only callers are unit tests (src/coordinator/miner_tests/compact_prepared.rs:510, prepared_expiry.rs:335).
- The runtime path behind `persist_issued_job` is `save_issued_record` -> `save_issued_job_compact` (src/coordinator/prepared_storage.rs:21-121; src/ledger/jobs/compact_issued.rs:131-172). Its post-lock fence is `require_revision`, message "payout revision changed while observing chain state" (src/ledger/connect.rs:495-508), preceded by `revalidate_issued` -> "payout snapshot stale".
- mod.rs:445-451 checks only `persist_issued_job(...).is_err()`, and `persist_issued_job` maps every error to `protocol_error("backend-rpc-unavailable", "job persistence unavailable")` (src/coordinator.rs:2030-2041). So a pool outage, a fingerprint-pin mismatch, or an elapsed issued deadline all pass this assertion.
- mod.rs:458 `job.context.prepared.snapshot.payout_revision == original` compares an immutable `Arc<PreparedSnapshot>` with a value read from the same Arc at line 410; it cannot fail.
- Concrete scenario: delete `require_revision` from `save_issued_job_compact`; this PR's test still passes (save_job still errors; persist still errors via revalidate_issued or not at all — either way the runtime fence regression is invisible).
- Report md lines 92-94 claim the run "verifies the exact original ... fence"; that sentence describes `save_job`, not the runtime.
- Fix: drive `ledger.save_issued_job_compact(job_id, payload, original, &job.wire.previousblockhash, expires_at_ms, prepared.reservation.dependency(&prepared.storage_key), None)` directly under the held lock and assert "payout revision changed while observing chain state"; keep the public `persist_issued_job` call but assert the row count only (already done at mod.rs:452-457). Drop the `save_job` half and the tautology at 458.

### 3. MEDIUM — report JSON hard-codes configuration and omits the two listener limits that actually gate a 2,000-session fan-out (EP-OBSERVABILITY, honest benchmark claims)
- mod.rs:287 emits literals `runtime_threads:2, build_workers_per_frontend:2, database_connections_per_frontend:4` instead of reading `frontend.config.build_workers` / `.database_connections` (`Coordinator.config` is `pub`, src/coordinator.rs:209). If the tokio attribute or fake_qbitd defaults change, the JSON silently lies.
- Not recorded anywhere (JSON or md): `initial_job_limit` = 128 permits per listener (src/stratum.rs:206, from `..Default::default()` at socket.rs:34; production default is the same via PRISM_STRATUM_MAX_PENDING_INITIAL_JOBS, stratum.rs from_env) and `initial_job_timeout_seconds` = 30 s applied separately to build and to persist (stratum.rs:878-921). `deliver_job` acquires that semaphore before every `build_job` (stratum.rs:862-867), so 2,000 sessions drain through a 128-wide window; md line 34 "Admission is explicitly 2,000 per frontend" describes only `connection_limit`.
- On timeout the session sets `retry_job` and retries on the 1 s timer without disconnecting (stratum.rs:1461-1471). A client delivery observed at e.g. 35 s is therefore a second attempt; the harness cannot attribute it because `metrics()` (mod.rs:157) keeps only `qbit_prism_database_*` lines and no listener delivery/retry counters are captured.
- Fix: read the three literals from `config`; add `initial_job_limit`, `initial_job_timeout_seconds`, `write_timeout_seconds` to the JSON; capture listener delivery failure/retry counts across the bracket (StratumStats or the `pending_job_builds`/delivery metric families), and state the 128-wide admission window in the md.
- Related nit: `settings` (mod.rs:101) is rebuilt from hard-coded "on" strings after the check; store the observed row instead.

### 4. MEDIUM — durability check is one-directional; orphan/duplicate persisted rows from a timed-out-then-retried persist are invisible (EP-ERRORS, durable row identity)
- mod.rs:347-352 verifies every delivered job ID has a live row with the right prepared key/parent/revision. Nothing verifies the converse.
- Scenario: under 2,000-session contention a session's `persist_issued_job` exceeds the 30 s listener timeout after the ledger transaction has committed; the future is dropped, the row stays, `retry_job` fires, a second job is built and persisted and delivered. The harness prints `B275_DURABILITY ... verified=true` while the persistence path did double work and the settlement lock was held twice for that session — exactly the cost #275 is measuring.
- Fix: per frontend, `SELECT count(*) FROM qbit_prism_jobs WHERE instance_id=$1 AND job_id<>$2` (prepared key excluded) on the uninstrumented `direct` pool and require equality with delivered count; report the difference as `orphan_rows` when non-zero rather than failing silently.

### 5. MEDIUM — two hand-rolled teardown paths in `Fixture::open`/`close` (cleanup architecture)
- mod.rs:103-114 is a second teardown that differs from `close()` (118-146): it does not close `direct`, has no timeout on DROP SCHEMA, and relies on `Listener::drop` abort instead of joining tasks. `node` is dropped implicitly in both.
- Judo: open `direct` and `node` before `CREATE SCHEMA` (a search_path naming a not-yet-existing schema is legal), build the `Fixture` with empty `frontends`/`listeners` as soon as the schema exists, push into it, and route any setup failure through the single `close()`. The `match opened { Err(..) => ... }` branch disappears. Same shape fixes the e2e copy if finding 2 is done first.

### 6. LOW/MEDIUM — gate + run boilerplate repeated four times; `throughput_floor` already models the Ci/Explicit distinction
- b275_persistence_measure.rs:10-57 repeats `gate::database_url` three times and `gate::required_database_url` once, plus `support::run(&raw, n, |f| ...boxed_local())`. tests/throughput_floor.rs:1705-1713 already uses `Selection::{Ci, Explicit}`.
- A `support::case(Selection, &[usize], Case)` with `enum Case { Delivery(usize), LandingLock, RevisionFence }` dispatched inside `run` removes the higher-ranked `FnOnce(&Fixture) -> LocalBoxFuture` closure and the per-site `.boxed_local()`, and makes "which gate" a typed argument instead of a copy-paste difference between lines 11 and 48.

### 7. LOW — `metric_delta` monotonicity invariant lives in the caller's prefix choice (EP-OBSERVABILITY)
- mod.rs:157 keeps every `qbit_prism_database_*` line except `_bucket{`; both families are histograms today (src/metrics/registry.rs:69-70) so deltas are monotonic. The delta helper (208-229) reports any negative or non-finite value as "metric counter reset"; widening the prefix to any gauge turns every decrease into a fake reset, and a NaN parse is mislabeled as a reset. Filter on `_count`/`_sum` suffix inside the helper so the invariant is in code.
- Unknown-vs-zero is preserved correctly: a family with no observations renders nothing (`Sample::Pending`, registry.rs:252), so it is absent from the JSON rather than reported as 0.

## Verified as correct (no finding)
- Clock bracket: `start` is taken after `set_tip` and before the `join_all` futures are first polled (mod.rs:251-266). `Coordinator::new` spawns no poll loop or timer (src/coordinator.rs:557-670), so nothing can refresh before `start`. `refresh_once` publishes synchronously through `CompactPublicationGuard::publish` -> `refresh.send_replace` (src/coordinator/prepared_storage/compact.rs:150-160), so `refresh_return_seconds` <= delivery time. One absolute `deadline` covers all refreshes (`timeout_at`) and all client reads (socket.rs:147). `receive` requires new job ID and `clean_jobs == true`: params[1] is prevhash and params[8] is clean_jobs (src/codec.rs:463-465); `deliver_job` sets clean_jobs when prevhash or revision changes (src/stratum.rs:895-898). No notify can precede the authorize reply (retry_job is set after `result()` at stratum.rs:1175-1176 and deliver_job runs after `request()` returns), so socket.rs:115-118 is safe.
- Fixture parent values: fake node starts at tip "ab"x32 (tests/support/fake_qbitd.rs:98-101); `set_tip("ef"x32, "ab"x32, 101, "02")` matches the signature (119). Repeated-byte hashes are invariant under Stratum word swapping, as the comment says. `wire.previousblockhash` is the raw parent (it is compared to `dependency.parent`, jobs.rs:69-71), so the SQL `parent_hash=$2` check is consistent.
- Settlement lock: constant 0x505249534d000003 matches src/ledger.rs:64; pg_locks query uses classid=high 32 bits, objid=low 32 bits, objsubid=1, correct for a bigint advisory lock. `Ledger::lock` is a blocking `pg_advisory_xact_lock` timed by `WaitGuard` (src/ledger/connect.rs:443-467), so the 3 s stub produces a real waiter and one settlement-lock sample; `settlement_waiter_observed: true` is printed only after `released?` propagated the waiter result (mod.rs:385-393). `lock_free_acceptance_met: false` and `commit_seconds: null` are hard-coded honestly.
- `direct` pool has exactly 2 connections: one for the fixture transaction, one for the waiter poll. Sufficient for both lock cases; a third concurrent query on `direct` inside those cases would deadlock on acquire (worth a comment).
- Durable identity checks in `delivery` use real fields: `CompactPrepared.{payout_revision, window, audit_hashes}` with `PartialEq` (src/ledger/jobs/prepared.rs:35-58), `StoredCompactPrepared.record` (102-104), `WindowRef.shares: Option<ShareRange{share_count}>` (src/ledger/window.rs:38-53), `PreparedSnapshot.payout_revision` (src/coordinator/compact_runtime.rs:8-12). Immutable-readback comparison (mod.rs:353-361) is meaningful.
- Config fields set at mod.rs:77-80 exist and defaults are as documented (fake_qbitd.rs:218-270: database_connections 4, build_workers 2, poll_interval 1 s unused because no loop runs).
- Gate: `required_database_url` (test-gate lib.rs:445-447) runs before any fixture in the ignored scale test; three CI tests registered in test/prism-gated-tests.txt in sorted position; the ignored test is unregistered, matching `throughput_floor` precedent and `check_gate_manifest.py` semantics (unexpected executed tests are problems, hence the "fresh manifest paths" instruction in the md).
- Entry validation: `(1..=2).contains(&count)`, `sessions > 0 && sessions.is_multiple_of(frontends)` (stable since Rust 1.87; toolchain pin 1.98.1), PG version bounded to 16.x, durability settings compared to "on". `p50` is the lower median (index (n-1)/2); label it as such or document.
- 2,000 TCP sessions: `connection_limit 2000` per listener; login concurrency 32; the md's ~4,000 fd note is right for one process; 1x2000 vs 2x1000 both run under the same per-listener limit. The unstated limiter is the 128-wide initial-job window (finding 3), not the connection limit.
- Panic path: `AssertUnwindSafe(...).catch_unwind()` runs `close()` before `resume_unwind` (mod.rs:189-198); `run`'s 240 s timeout does not cover `close()` (up to 15 s per listener + 15 s DROP), acceptable.
- Advisory locks are database-wide; `SERIAL` serializes cases within the binary and cargo runs test binaries sequentially, so cross-binary contention is not an issue.
