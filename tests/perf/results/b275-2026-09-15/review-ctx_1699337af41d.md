## Ranked findings

FINDING 1
FILE: crates/qbit-prism-server/tests/support/b275_persistence_measure/mod.rs:262-301 (delivery bracket, `complete`), socket.rs:27-43 (per-listener StratumConfig; `stats` discarded)
SCENARIO: The harness cannot see a failed-then-retried delivery, so a run that hit a persistence failure or timeout is reported as `complete: true` with an inflated latency and no error. Verified runtime path at base: `deliver_job` (src/stratum.rs:884-921) wraps `build_job` and `persist_issued_job` in the default `initial_job_timeout_seconds = 30.0` (stratum.rs:203); on `Err`/timeout it sets `session.retry_job = true` and returns a `StratumError`; the session loop (stratum.rs:1462-1472) swallows `StratumError`s and re-runs `deliver_job` on the next 1-second `timer.tick()`, which builds a NEW job ID and sends a `mining.notify` with `clean_jobs=true` (prior job is old-parent, stratum.rs:894-898). The harness client accepts any new-parent notify with a fresh ID (socket.rs:141-155), so the retried delivery counts as a success. The only counters that record the failure are `StratumStats::job_delivery_failures` (stratum.rs:404-416), which live in the `StratumConfig` built inside `Listener::start` and are never read; the harness keeps only `qbit_prism_database_*` families (mod.rs:157), where a failure appears only if the timeout fired during the advisory-lock wait itself (`WaitGuard::drop`, src/ledger/connect.rs:416-422), and nothing asserts on failure-labelled samples. Concrete case: 2,000 sessions on one frontend serialize every `save_issued_job` behind the DB-wide settlement advisory lock plus a 4-connection pool; if the tail exceeds 30 s the last sessions time out, retry ~1 s later, and the JSON shows `received: 2000, complete: true, max ≈ 31-40 s` with empty `delivery_errors`. Secondary (EP-ERRORS): the timed-out first attempt may already have committed its row (timeout after side effect); the durability check (mod.rs:342-352) only counts delivered IDs, so the orphan row is invisible. Also unstated in the JSON/report: the per-listener `initial_job_limit` of 128 permits and the 30 s per-phase timeout, both runtime defaults the harness inherits and which bound the measurement.
SEVERITY: Medium (benchmark honesty / EP-OBSERVABILITY: failed-and-retried is indistinguishable from clean; does not affect the three ordinary gated tests at 8 sessions, per the author's smoke numbers).
SUGGESTED FIX (author's call): keep `config.stats` in `Listener`, report `job_delivery_successes/failures` deltas per frontend in the JSON, and make `complete` require zero failures; or at least require zero `outcome="failure"` lock-wait samples; document the 128-permit build admission and 30 s phase timeout as configuration.

## Riskiest areas attacked with no refutation found

1. Clock bracket and event attribution: `start` is taken after `set_tip` and immediately before `tokio::join!` polls `refresh_once`; `refresh_once` first RPC is inside the bracket; the runtime persists before notify (`persist_issued_job` at stratum.rs:903-921 precedes `write_json(notify)` at 934), so delivery time includes durable persistence as claimed; refresh publication signals sessions through `send_replace` (coordinator/prepared_storage/compact.rs:161) and each session's receiver is a clone taken at accept, so the pre-bracket refresh cannot wake sessions; client timestamps use the same `Instant`; the 120 s deadline is absolute (`timeout_at`) and not reset per frame; no poll loop, timer or publisher is spawned by `Coordinator::new` (coordinator.rs:557-700).
2. Unknown/failed vs zero: `complete` requires every session received and no refresh error; `max`/`p50` are `null` when nothing arrived; `refresh_return_seconds` is `null` per failed frontend; `commit_seconds` is `null` with an explicit reason; `metric_delta` rejects negative/non-finite deltas; only two `qbit_prism_database_*` families exist at base and both are histograms (metrics/registry.rs:69-70), so no gauge can trip the "counter reset" check; render emits no timestamps; `_bucket{` filtering leaves `_count`/`_sum`; overlapping-sum caveat is stated in the JSON.
3. Durable row identity: `save_issued_job` binds `payload.prepared_key`, `parent_hash`, the dependency's original revision and a timestamptz expiry (ledger/jobs.rs:63-140), matching the SQL at mod.rs:347; `compact_prepared` re-read equality checks immutability; job IDs embed instance_id so the cross-frontend duplicate check is meaningful.
4. Input boundaries / gate: `measure_2000...` uses `required_database_url`, which never skips (test-gate lib.rs:445); ordinary tests skip only without `PRISM_TEST_REQUIRE_INTEGRATION`; `ensure!(sessions > 0 && sessions.is_multiple_of(frontends))` (MSRV pin 1.98.1 covers `is_multiple_of`); frontends bounded to 1..=2; `ConnectionLimit::new(2000)` yields exactly 2,000 permits (stratum.rs:224-236); shard script discovers the new binary via `cargo metadata` and never passes `--ignored` for it, so CI runs exactly the three registered names.
5. Cleanup / partial failure: setup failure closes listeners, ledger pools, drops the schema and reports both errors; `Fixture::close` closes listeners (10 s join + abort inside `run_listener`), then pools, then `DROP SCHEMA` under a 15 s timeout; the 2,000 `SessionId` drop tasks (ledger/connect.rs:103-118) that fire DELETEs after listener shutdown only log warnings once the pool is closed or the schema is gone, and sqlx `close()` waits only for checked-out connections, so no hang path was found; `catch_unwind` runs cleanup before `resume_unwind`. Shared 240 s outer timeout wraps the body but not `close()`; no unbounded await inside `close()` was found.
6. Two-topology fairness: each `Listener::start` builds its own `StratumConfig`, so 2x1000 gets two independent 128-permit build semaphores and two 4-connection pools; this equals separate-process semantics and is consistent with what the report claims, but the semaphore is not listed as configuration (see Finding 1).
